# Trenz canvas operations contract

Read this file before calling `canvas`, `canvas_tasks`, `assets`, or `upload_file` for a canvas. Fields, models, enums and error codes come from the current MCP schema; this file only sets the cross-tool execution strategy and does not copy interface parameters. When you need to write prompts for images, storyboards, videos or voiceover, also read [Storyboard and video prompt templates](prompt-templates.md).

In this file, "canvas" means the Canvas that holds nodes and edges; "storyboard" means one Storyboard image generated on the canvas and used to constrain a video. Do not mix the two.

## User and cost boundaries

- Creating a canvas requires the **Pro or Scale plan** on trenz.ai. Canvas calls run on the user's trenz.ai plan and count toward the plan's 7-day Agent allowance; canvas generation also uses trenz.ai credits. Costs follow the current tool descriptions and responses; do not convert between the 7-day allowance and credits.
- Before canvas writes or generation, call `account_info` to read the current credits balance; field details, balance meaning and usage display come from the current tool description and response. `account_info` does not prove that the user has canvas write permission (the Pro or Scale plan).
- **Every paid generation needs the user's explicit confirmation first**: before calling `canvas.generate`, show the final concept/script, the actual prompt, the reference assets and their roles, model, count, duration, aspect ratio, resolution or image size, reference mode and any known cost, then stop and wait for explicit approval. An initial "generate it for me", providing assets, confirming the creative direction, or silence does not approve the final paid job.
- The user may confirm a complete batch task list at once. After confirmation, any material change to the prompt, reference assets/roles, model, count, duration, aspect ratio, resolution/image size or reference mode needs a new confirmation; redos, variants and retries are new paid submissions and do not inherit the old confirmation.
- On a balance or permission error, a timeout, or any other response without a `task_id`, stop the current submission and report the state. Do not retry blindly, do not generate extra variants, and do not share, publish or delete the canvas on your own.

## Creation stage gates

1. **Settle the content first, draft at no cost**: for a video project, first agree with the user on the target audience, core selling point/emotion, hook, script, CTA, shot beats and factual boundaries, then write the confirmed content into text nodes. Images that serve the video, such as concept art, character/scene design images, first frames and storyboards, follow the same gate. A standalone product image or single-image task only needs the image's goal confirmed; do not force a video script on it.
2. **Build the skeleton, do not submit generation**: after creating the canvas, only build the setting/script text nodes, reference nodes from uploads or the asset library, empty output nodes with complete render fields, and real edges. Do not call `canvas.generate` at this stage. Before uploading, state the cost per the current `upload_file` tool description; the later PUT does not request a new upload URL.
3. **The user visually confirms the skeleton**: through the canvas page or actual previews after `hydrate`, let the user check that every reference image is correct, clear and complete, that the roles (main identity / detail / scene / style) and reference links are right, and that the script and target output nodes are complete. Reporting only file names, node names or storage coordinates is not visual confirmation. Stop until the user explicitly confirms; adding or replacing reference images, or changing roles later, reopens this gate.
4. **Generate images/storyboards after confirmation**: if the user does not specify an image model, default to `gpt_image_2`; if the user explicitly names another model the current schema supports, use it. Only submit after writing the final prompt and `generationDraft` parameters back to the node and confirming per "User and cost boundaries". When a storyboard is done, first check subject consistency, shot readability and text hierarchy, then let the user visually confirm it; do not use it for video generation until the user has confirmed that storyboard.
5. **Video parameters come from the script and the user together**: duration comes from the confirmed script timeline; shot timecodes must be continuous and add up to the submitted duration, and voiceover must fit naturally in its time slot. First give one model recommendation with reasons based on the script, assets and budget, then let the user confirm the model, resolution, aspect ratio and reference mode. The current modes come from the schema; the usual mapping is all-round reference `reference`, first frame `first-frame`, first and last frame `first-last-frame`, no reference `none`. After confirmation, write the model, resolution and `inputMode` explicitly into `generationDraft`; do not rely on platform defaults or automatic derivation. If the model does not support the duration or parameters the script needs, revise or split the plan and confirm again; do not cut or stretch the script on your own.
6. **Check the confirmed version before submitting**: get the latest revision again, and check that the target node's prompt/`generationDraft`, reference edges, `input_node_ids` and asset roles still match the version the user confirmed. Any material change must be shown and confirmed again before calling `canvas.generate`.

## Default interaction: work with the user through the canvas page

1. When actually working on a canvas, once you have a valid canvas ID, open the canvas in the built-in browser if the current session provides one. The canvas page is the shared workspace between the user and the agent: the user can see the nodes the agent writes at any time, and can inspect and edit the canvas directly.
2. The canvas base URL is `https://www.trenz.ai/app/create/canvas/{canvas_id}`. When the user gives a canvas ID, first `load` to confirm the canvas exists, then open the base URL. When the user gives a full URL, extract the ID, confirm it with `load`, and keep the original URL's `nodeId` when opening it. When creating a new canvas, open the base URL after `create` returns the ID.
3. The built-in browser's login state is usually separate from the user's everyday browser, so the first visit will likely land on the login page. Calling the open tool only starts navigation; only say "the canvas is open" when the result confirms the canvas page loaded, or the user explicitly confirms they see the canvas. If it lands on the login page or the page state cannot be confirmed, ask the user to log in or check the page in the current built-in browser, then stop and wait for their reply. Never ask for, fill in or store the account password.
4. After the user confirms they have logged in, reopen the full canvas URL from before login. Do not rely on the post-login home page, workspace or any other default redirect, and do not just refresh the login page; if the original URL had a `nodeId`, reopen that same node URL.
5. After `canvas.generate` succeeds, build the node link from the same call's `canvas_id` and the `execution_node_id` in the response: `https://www.trenz.ai/app/create/canvas/{canvas_id}?nodeId={url-encoded execution_node_id}`, and open it the same way so the user sees the element just generated. If it lands on the login page, handle it per items 3–4. Always use `execution_node_id`, not the `target_node_id` you submitted, because when the target node already has content the generation lands on a new version-branch node. `nodeId` is only a navigation parameter of the web page, not a request parameter of the `canvas` API.
6. Within the same task, reuse a canvas page that is already open with a confirmed login; do not reopen it after every API call. Opening the canvas and the user finishing the visual confirmation of the skeleton are two different states: being on the canvas page does not mean the user has confirmed.
7. If the current session has no built-in browser, or opening fails, say so plainly and give the user the current base URL or node URL to open manually. This does not block later API operations, but steps that need the user's visual confirmation must still happen through the canvas page or actual previews.

## Execution boundaries

- When the user gives a canvas URL or ID, or asks to continue, `load` first; a response without `document` means the canvas was deleted, so do not create a replacement. For other canvas creation requests, `create`.
- All canvas actions go through `canvas({action, params})`. Nodes, edges, renames and asset attachments go through `apply.operations`; they are not separate tools. Every write uses the latest `expected_revision`; on 409, retry only the same intent, and stop after 5 conflicts in a row.
- Local or attached files enter the canvas through `upload_file`. After the PUT, check the remote byte size, then attach using the returned coordinates. Uploads do not go into the `assets` library automatically.
- Reference images/text must affect the target node through real nodes and edges; pass `input_node_ids` only when you need to narrow the references or fix their order. Normal generation uses the node's `generationDraft`; do not replace the long-lived draft with a one-off top-level prompt.
- Canvas generation is submitted with `canvas.generate` and then queried only with `canvas_tasks`; do not mix it with `ai_generate`'s `check_task`. If `generate` fails without a `task_id`, first read `generation_diagnostic` in the MCP response: it has already reloaded the same canvas target node and safely returns `status`, `attempt_id`, `error_code` and `error_message`. Diagnose the root cause from its `error_message`, not from the outer 4xx/5xx. If the field is missing or the MCP is an older version without it, `load` manually and check the node's `data.generation`. On success, record the `task_id`; backfill or reuse completed assets first instead of generating again.
- Check images as the task requires. For videos, by default hand the result to the user for review after submission; only when the user asks you to wait or check quality, `hydrate` and check duration and visual problems, and first locate whether the cause is the assets, the storyboard, the prompt or the model before deciding to redo.
